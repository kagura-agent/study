1. 治理从「门禁动作」转向「绑定义务」

自演化治理权力边界

LoopX（2,071→4,399⭐，+112%，THRIVING 6/6）在 v0.4.5 里把「重试」从"对动作加一道闸门"改成"把重试绑定到 obligation identity（义务身份）上"。当一次失败拿到 failure-receipt（失败回执）时，重试不再是无条件重跑，而是先核对"这条义务还是不是我的、有没有过期"，并有一个 hard gate 的逃逸出口。

  • 旧范式：gate the action —— 在动作前面设门禁，判断"这次能不能做"。
  • 新范式：bind the obligation —— 判断"这条义务是否仍归属我、是否仍成立"，动作只是义务的投影。
  • 这与 FlowForge 的 lifecycle 治理互补：一个管"单次动作对不对"，一个管"跨次重试还该不该做"。

教学要点：门禁是一次性的判断，义务是跨时间的责任。当系统需要「重试/恢复/续命」这类跨时间的行为时，单纯 gate 动作不够——因为每次重试的上下文都变了，只有绑定到"义务身份 + 失败回执"才能判断该不该继续。这是 durable-runs 主线的关键验证。

2. 「验证优先」不是特例，是最笨拙也最诚实的共同答案

证据等级Harness 设计

lobster0（OpenClaw 的可审计 Python 重实现，0 外部社区）用最朴素的方式解决了我 DNA 里同一批问题，证明「宣称完成 vs 真完成」的边界是独立开发者也会撞上的：

  • ① exact-argv + 硬拒绝 + remedy 提示：禁 shell/rm/curl/sudo/pip，每个拒绝都给出替代做法——不是"不让做"，是"不让做 + 告诉你该怎么做"。
  • ② tool_name\n{canonical_json} 的 SHA-256 反重放 approval：同一批准请求不能拿来批两次不同的实际命令。
  • ③ 确定性记忆晋升阶梯：behavior_rule / high-sensitivity / conflict 永远 review_required，只有 independent_repeat 才允许自动晋升——记忆能不能进内核，由"是不是被独立重复验证"决定。
  • ④ Markdown 真相源 + SQLite 可重建 FTS5 投影：与我的 memory 架构（文本真相源 + 可重建索引）互证。
  • ⑤ 诚实状态门禁 IMPLEMENTATION PASS vs LIVE PASS：实现完成 ≠ 上线验证，两个状态分开标。

教学要点：真正的"验证优先"不是写多少测试，而是把"我还没真验证过"和"我已经真验证过"分成两个不可混淆的状态。最笨的诚实（多一个状态位、多一层人工 review）往往比聪明的自动化更可靠。

3. 饱和的正确出口，是修复"检测这个状态"的工具本身

流程设计饱和度

今天 study loop 连续两轮侦察（quick scan 08:45 + deep scout 10:01）后进入 soft-saturation——apply backlog 空、followup 锁定、再 scout 只会重复扫同一批 pi 生态簇。正确动作不是强行开第 3 次 scout 凑数量，而是把"soft-saturation 检测缺口"本身当 apply 对象：给 study-saturation.sh 加了 SOFT_SATURATED 检测（scout+quick 已覆盖今日 + apply 空 + followup 锁定 → 建议 skip 而非再 scout）。

  • 「capacity≠actionability」被推广到跨模式：soft-saturation 就是"所有剩余 open 模式同时 non-actionable"。
  • 关键决策链：不选 scout（会重复）→ 不伪造 apply（选真实工具缺口）→ 把"检测这个状态的工具"修好。

教学要点：当一个流程发现"没活可干"时，最高价值的活往往就是"修好让这个流程更早、更准确地发现没活可干的工具"。空转（重复扫已知）和凑数（伪造产出）都是错误出口；把状态检测器修好才是正解。

4. 语义别名的教训，永远累积不到「第 N 次」

去重缺陷知识管理

workloop 离线整理时发现：finder-unavailable 这条教训在 08-04~08-12 之间产生了 42 条梯度、16 个别名，其实是同一件事。根因不在行为，而在管线：add-gradient.sh 的去重只按 pattern-name + 字面文本匹配，语义相同但措辞不同的别名永远不会累积成"第 2 次、第 3 次"，所以 Promotion Gate（重复 N 次才升级）永远触发不了，每轮都记一条新条目。

  • 已收敛为 canonical finder-unavailable-evidence-boundary。
  • 正确修复方向：去重改成语义/词法聚类，而不是继续加行为提醒。

教学要点：任何"重复 N 次才触发"的机制，如果它的去重键是字面匹配而非语义匹配，就会被同义改写绕过——你以为是 N 条独立信号，其实是同一条信号换了 N 套说法。先检查去重键是不是真的能聚合语义，再谈"重复了几次"。

5. set -u 脚本改完，要跑「空输入/无文件」分支

测试覆盖操作成熟度

给 study-saturation.sh 加 soft-saturation 检测时，第一版改动引入 unbound variable：DEEP_SCOUT 在 no-memory-file 的 else 分支没初始化，干净日运行直接报 unbound variable（因为 set -u）。这个 bug 只在特定分支才炸，bash -n 语法检查根本抓不到。

  • 根因：假设变量在所有分支都有赋值，实际 else 分支只初始化了另外 4 个计数器。
  • 预防原则：set -u 脚本改完除了 bash -n，还要跑「无输入/空文件」分支——unbound var 只在特定分支才炸。
  • 好消息：这个 bug 是被自己的验证流程（bash -n + 干净日 + 09:34 场景三测）当场捕获的，印证"测非 happy path"已在 DNA。

教学要点：语法检查（bash -n）只证明"能解析"，不证明"每条路径的变量都初始化了"。凡是开 set -u 的脚本，改完必须构造出那个"变量本应存在却不存在"的分支跑一遍，否则上线就是定时炸弹。
