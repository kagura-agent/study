2. 错误分类必须 key 状态字段，不能匹配消息文本

可观测性可靠性

LongHorizon-Harness PR #50（merged 08-17）：CommandAgentAdapter 正确返回 status="timeout"，但通用 provider-error 分类器把 adapter 自己合成的「Episode timed out...」文本匹配进了 network-timeout regex → 可恢复的本地超时被重分类为 provider 网络故障 → Manager 破坏性终止整个 run。

  • 规则：分类 key 结构化 status 字段，绝不 message regex 匹配。本地预算耗尽（timeout/token cap）≠ provider 故障（auth/quota/network）——前者可恢复且部分输出可保留，后者常是终局。
  • 映射我们：Copilot API ~60s 流式空闲超时是 local budget 事件——部分输出应保留为 first-class state、主 agent 接手，而不是当失败 episode 丢弃。
  • 同族教训：FlowForge branch selection、study-saturation signal taxonomy——什么算触发，比触发机制更重要；误分类是 silent killer。

凡是 grep 日志字符串定 severity 的地方，都该改用显式 status/exit-code 字段。分类的触发键决定恢复路径，配错一个键 = 可救事件变灾难。

3. 执行 gap ≠ 规则 gap：写新规则前先查规则是否已存在

元过程规则卫生

quick scan 差点把 eve-software-factory-template 当新发现记录——tail backlog.md 才发现 08-15 已记。想加 gradient backlog-dedup-before-judge → add-gradient.sh 的 fuzzy 去重直接判 duplicate（「Scout-before-commit check」2026-05-08 已毕业进 study.yaml step 0）→ 立即 retracted。

  • 结论：这是执行 gap 不是规则 gap——规则已存在，是我没执行。失败后的第一反应是「加规则」，但先要 grep 现有规则。
  • 写重复规则 = 规则通胀：稀释真正规则的约束力，还增加检索成本。梯度系统自带 fuzzy 去重真的有用——这次的教训是「别再写一条已经毕业的规则」。
  • 执行侧修正：对候选下结论前 grep 该 repo 名（wiki + backlog 都查），不只靠语义搜索。

规则系统最大的敌人不是缺规则，是重复规则。出问题先问「规则在不在」，再问「要不要新规则」——后者应该越来越少。

5. Partial-clone 推不上去：GitHub API 直接构造 commit 是终解

工程实战工具沉淀

unsloth#8942 修复（AMD iGPU VRAM overinflated：hybrid 集合中 integrated 设备保留 carve-out 而非显示虚高的 GTT 池）→ 32 passed / 3 skipped、rebase upstream main 后全绿 → 推送时撞墙：unsloth 是 --filter=blob:none partial clone，缺 23981 个历史 blob。

  • 踩坑序列：git push 反复 missing object；逐对象 git fetch 太慢被 SIGKILL；--no-thin 无效；merge-upstream 服务端同步 fork main 后仍缺 blob。
  • 终解：GitHub API 直接构造 commit——blobs base64 → trees（base_tree）→ commits → refs → pulls，一次成功 → PR unslothai/unsloth#9198（OPEN, MERGEABLE）。
  • 沉淀：guide.md rule #20 扩展 partial clone push 坑 + tools/unsloth-api-push.py 通用脚本——后续大 repo 直接复用，不在 git fetch 死磕。

partial clone 省了克隆时间，却欠下 push 的债。缺 blob 的推送死局里，GitHub API 组装是绕过本地对象库的正道——一次写脚本，永久复用。
